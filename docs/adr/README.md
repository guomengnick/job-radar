# 架構決策紀錄（ADR）

每份 ADR 記一個決定：當時的情況、有哪些選項、最後選了什麼、代價是什麼，以及實測數字。
下面是目前的決定和依據。之後有實測數字時，把每一條展開成 `NNNN-標題.md`。

| # | 決定 | 狀態 | 依據／待補 |
|---|---|---|---|
| 1 | 用 Lambda，不用 Fargate 或 EC2 | 已決定 | 一天只跑幾分鐘。限制是單次最長 15 分鐘，用「最久沒檢查的先掃」來應對（見第 3、5 條）。之後如果要示範容器或 K8s，再評估 Fargate |
| 2 | 用 DynamoDB 隨需計費，不用 RDS 或 S3 | 已決定 | 不需要 VPC 和 NAT；條件寫入可以同時判斷「是不是新的」和去重。代價：臨時查詢不方便 |
| 3 | 新職缺用 ID 判斷，不用發布日期 | 已決定 | 漏跑幾天也不會漏抓，沒有日期的職缺也抓得到。看板第一次成功抓取時，當下所有職缺當作基準線，不發通知 |
| 4 | 死看板策略：連續 3 次 404 判定為死，之後每 7 天檢查一次 | 已決定 | 2026-10-11 抽測，每家 1,300 個看板中回 404 的比例：Greenhouse 36%、Lever 55%、Ashby 24% |
| 5 | 每家 API 每秒 15 個請求，同時最多 16 個 | 已實測 | 2026-10-11 本機測試：每家 900 個看板，0 次被限速。Greenhouse 全部掃完約 9 分鐘。部署後看 `BoardsThrottled` 指標再調整 |
| 6 | 區域選 ap-southeast-2（雪梨） | 已決定（受限） | 原本選 us-west-2，因為目標 API 都是美國公司。2026-10-13 部署時發現：帳號所屬組織的 SCP（AdvancedModeRegionRestrictionSecurityControlPolicy）只允許 ap-southeast-2，逐一測試全部 17 個區域後確認。選擇保留這道防護，不修改 SCP。代價：到美國 API 的延遲增加，但掃描時間主要受每家每秒 15 個請求的限速影響；第 5 條的本機實測也是從台灣跨太平洋連線，延遲量級相近。待補：部署後看 Lambda 執行時間 |
| 7 | 用 Terraform，不用 SAM 或 CDK | 已決定 | Terraform 是目標職缺 JD 上最常見的阻礙；可以一個指令重建或刪除整套環境 |
| 8 | 設定檔編進程式（go:embed），不在執行時讀取 | 已決定 | 規則有版本紀錄、改動要經過 review；代價是改規則要重新部署 |
| 9 | 排程分開觸發，暫不用 SQS 或 Step Functions | 已決定（第一版） | 三家 ATS 各自一個 Lambda 就能在 15 分鐘內跑完。等看板數或執行時間超過時，再改成 SQS 分派加 DLQ |
| 10 | 通知用 Telegram | 已決定 | 免費、一個 POST 就能送出。LINE Notify 已在 2025 年停止服務 |
| 11 | 指標不設維度 | 已決定 | 每多一個維度值，計費的指標數就倍增；各 ATS 的明細改存在 runs 表和日誌 |
| 12 | 104 和 LinkedIn 的職缺從通知信讀，不爬網頁 | 已決定（2026-10-20） | 104 沒有 API，網頁有 Cloudflare 擋機器人，不繞過。SES 收信存進 S3，ingest 解析；LinkedIn 的職缺配對通知由 Gmail 篩選器原樣轉寄（2026-11-04）。代價：只看得到信裡有的欄位；要自己的網域、Route 53 和 DKIM；Outlook 轉寄會破壞 104 的 DKIM 簽章，改看 Microsoft 的驗證結果；LinkedIn 連結裡的一次性登入碼不保留，只留職缺編號 |
| 13 | 要讀職缺頁面時，用使用者自己的瀏覽器（Chrome 擴充功能），按了才讀 | 已決定（2026-10-21） | 跟本人點開一樣，不是機器人。`activeTab` 只在按下時讀目前這一頁；批次功能才讀其他開著的 104、LinkedIn 職缺頁。開分頁也是按了才開，每 3～5 秒隨機一個。代價：只在裝了擴充功能的電腦能用，沒有背景自動讀取 |
| 14 | 擴充功能呼叫 Lambda Function URL，靠共享密鑰，不用 API Gateway 或使用者帳號 | 已決定（2026-10-21） | 擴充功能不能簽 AWS 請求，而且只有一個使用者。沒有密鑰的請求在讀任何東西之前就被拒絕。擴充功能和伺服器互報版本，太舊的擴充功能收到 HTTP 426 和「請重新載入」。代價：網址是公開的，密鑰是唯一的門；外洩時要換（見 `extension/README.md`） |
| 15 | AI 只能呼叫一個工具 `record_assessment` 回答，每個值都檢查 | 已決定（2026-10-21） | 職缺頁面是不可信的輸入，可能夾帶給 AI 的指令（prompt injection）。模型不能做任何動作，只能填固定格式；值會先夾在允許範圍內、對照允許的選項才使用；Telegram 訊息裡每個欄位都跳脫。第一次上線就回 HTTP 400：新模型不接受「強制指定工具」，改成提示詞要求呼叫一次，沒呼叫就算失敗。代價：每頁約 0.02～0.04 美元；結果是判斷不是事實，所以附上原文引用，JD 也存一年供對照 |
| 16 | 批次評分用 Message Batches（半價），每 10 分鐘輪詢結果 | 已決定（2026-10-23） | 一次可以送幾十頁，價格減半。Anthropic 做完不會主動通知，所以 batch-check 每 10 分鐘看一次；沒有未完成的批次時不讀任何密鑰，大部分執行幾乎不花錢。代價：結果最久 24 小時才回來（通常一小時內）；送出超過 26 小時還沒結束，Telegram 提醒一次 |
| 17 | 評分失敗分三級（永久、暫時、不明）；暫時和不明自動重送最多 2 次，之後進 DLQ | 已決定（2026-10-28） | 由 API 回的錯誤類型決定。請求無效或太大、權限、帳務是永久的，重送也一樣失敗，直接進 DLQ；忙碌、限速、伺服器錯誤、逾時、批次過期是暫時的；其他算不明，跟暫時一樣重試，但分開計數。重送用保存的 JD，不必重開網頁。DLQ（死信佇列，SQS，保存 14 天）不是空的就告警，修好後 `make redrive` 重跑。代價：多一個佇列和一個告警 |
| 18 | 部署用 GitHub Actions：OIDC 換臨時憑證，加人工核准，不存 AWS 金鑰 | 已決定（2026-10-25；10-29 啟用） | PR 用唯讀角色跑 `terraform plan`，讀不到密鑰參數。部署要按按鈕，只能部署 main，在 production 環境等人核准；核准後用同一個 commit 再 plan 一次，摘要變了就停，最後印出每個函式跑哪個 commit。10-29 第一次走 OIDC 失敗：這個 repo 的權杖用 GitHub 不可變的 subject（帶擁有者和 repo 的數字 ID），改成信任這個格式；repo 刪掉重建會換 ID，所以搶不走這兩個角色。代價：repo 和 Actions 日誌是公開的，帳號 ID、信箱、chat ID 都要遮掉 |
| 19 | 每筆評分記下評分檔案的版本和程式的 commit | 已決定（2026-10-29） | 當時要證明 10-29 那批是用哪一版規則評的，得翻日誌、S3 的批次封存和 SSM 參數歷史。之後每筆評分存 `profile_version` 和 `commit`，Telegram 最後一行顯示；批次送出到讀回之間有部署時，寫成「舊→新」。評分檔案換版後，兩週內評過的職缺也會重評。代價：在這之前的評分沒有這兩欄 |
| 20 | 已投紀錄放在 jobs 表，讀出來在記憶體比對，不另開表、不用 PostgreSQL | 已決定（2026-11-05） | 投遞紀錄（`104-applied#代碼`）和職缺放同一張表，用現有的 `source-index` 依時間全部讀出（11-05 時 25 筆，最多幾百筆），在記憶體比對：同一個職缺標 ⛔，同一家公司的其他職缺標 ⚠️，分數不變。不寫回每筆職缺，所以剛投的馬上生效、舊資料不用回頭更新，也不用新權限。公司名稱去掉「股份有限公司」等字後，相同就算同一家；「一邊包含另一邊」要短的那邊至少 3 個字，避免「科技」對到每一家。擴充功能上線前的投遞用 `radar applied-import` 補進來。代價：104 和 LinkedIn 的名稱不同（例如 104 寫中文名、LinkedIn 寫英文名）時對不到。要追蹤完整流程（已投→已讀→面試→錄取）或做臨時統計時，再評估 PostgreSQL |
